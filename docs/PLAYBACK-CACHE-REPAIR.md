# Playlist cache recovery — v0.7.0-rc4

A newly resolved representation could replace a speculative cache binding while the player retained an older format pin. A controlled reproduction on rc3 stopped with Media3 code 2000 / AudioFormatChangedException and did not recover within 60 seconds. Rc4 discards the conflicting binding and rebuilds the full sources at the same item and timestamp. One automatic attempt is allowed until another item or 30 seconds of sustained playback. The queue and play/pause intent are preserved; representation identity checks remain strict.

A second regression covers fully cached audio whose validated length was stored only for readiness. Media3 now receives that length too, including migration when an older entry is opened. This prevents an unnecessary network request to discover EOF. The player buffer label now excludes future queue items.

Verification on 8 November 2026: 64 JVM/Robolectric tests passed; release lint zero errors and 26 warnings. Pixel rc3 failed the controlled conflict; rc4 resumed from about 11 seconds to 13 seconds without manual retry. Six repeated starts of Yellow and A Head Full of Dreams and a natural next-song transition passed with screen-off and Bluetooth connected. A full saved-track read with a refusing upstream also passed. Tests were app-muted: audible quality and a longer real listening session remain owner checks. The controlled failure matches a possible route to reported interruptions, not proof of every historical incident.

Device checks require an existing saved Coldplay playlist and compatible test signing. Run PlaylistCacheReplayDeviceTest normally for replay checks, or pass instrumentation argument cacheConflict=true for the controlled replacement race. CachedEofDeviceTest reads the saved Yellow entry without allowing network access. Tests leave saved playlists unchanged; instrumentation restarts can lose the transient queue, so the fixture reconstructs it from the saved playlist.
